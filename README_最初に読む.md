# SHEET MASTER v4.0(完成版一式)

このフォルダは、そのままビルドしてアップロードできる Xcode プロジェクト一式です。
**ソースコードの変更・既存コードとの合体はしないでください。**(前回、旧画面と混ざって読み取り結果が表示されませんでした)

## 作業は3つだけ
1. 今のリポジトリの中身(アプリのプロジェクトとソース)を、このフォルダの中身に**丸ごと置き換える**。
   GitHub Actions などのアップロード用の設定ファイルは今のものを残してよい。
   その場合、ワークフロー内のプロジェクト名・スキーム名を `SheetMaster.xcodeproj` / `SheetMaster` に合わせる。
2. `Config.xcconfig` の3行(Bundle ID・Team ID・ビルド番号)だけを書き換える。
   Bundle ID は今の TestFlight のアプリと同じにする(同じアプリの更新になる)。
3. Release でアーカイブして TestFlight にアップロードする。

## 中身
- iOS 17 以上 / SwiftUI / 外部ライブラリなし
- バージョン 2.6、アイコン・カメラ/写真の許可文・暗号化申告(なし)は設定済み
- 共有スキーム `SheetMaster` 入り(コマンドラインからもビルド可)
  例: `xcodebuild -project SheetMaster.xcodeproj -scheme SheetMaster -configuration Release -destination 'generic/platform=iOS' archive -archivePath build/SheetMaster.xcarchive`

## もしビルドエラーが出たら
エラーの出た行の文法・型だけを直し、画面構成・読み取り処理・データの形は変えないこと。

## v4.0 の変更点(読み取りの精度を上げた。画面・データの形はそのまま)
対象の例: 日新電子工業 DM261405J-M003 鍵、ハンドル付不良品受箱(SUS304 t1.5)。
v3.9 では、斜めの辺やくびれがある箱を読ませると、実物と大きく違う板の分け方・形になっていた。
同じ図面をチャットのClaudeで段階的に読むと実物に近い形になったので、その読み方をアプリのAIへの指示に組み込んだ。

- **AIへの指示を追加**(`Reading/Prompts.swift`)
  - 【実物の写真】写真の中に実物の板(抜いた板・保護フィルム付きの板)があれば、板の分け方と外形をその写真に合わせる。回転・裏返しで写っていても、穴の並びや切欠きで向きを合わせる
  - 【手書きの展開メモ】「260/141.4/170 L=570.6」のような手書きの数字の列は、曲げ板1枚の断面の寸法と展開長として最優先で使う。「外」「内」「−0.8」(控除の合計)も読む。用紙の裏から透けた数字は無視する
  - 【輪郭が斜め・段で折れる箱】前板・後板は正面図の外形どおりの平板。左右の壁は輪郭に沿って何回も曲げる帯状の板(斜辺は45°曲げ)。前板の縁の一直線の範囲だけに側壁を曲げでつなぐ作り方も書いた
  - 曲げでつながない理由に「共有する辺が一直線でない(斜辺・くびれ・段)」を追加(`Reading/DrawingReader.swift` の読み直しの理由にも追加)
  - 段階Bに【帯状の側板】【前板+側板の一部】【実物の写真】の書き方と例を追加
- **曲げごとの控除値**(`Models/Models.swift` の `Bend.deduction`・`FaceFlange.deduction`)
  - 図面に手書きの控除(例: 45°×2で「−0.8」)があれば、AIがその曲げの deduction に1回分の値(0.4)を入れ、アプリはそれを使う
  - AIへの回答の形(スキーマ)に、bends と flanges の deduction を追加(省いてもよい項目)
- **45°など90°以外の曲げの控除の計算を直した**(`Geometry/Geometry.swift` の `bendDeduction`)
  - v3.9までは「90°の値 × 角度/90」の比例計算だったため、45°の控除が大きすぎた(SUS t1.5で1.4。現場の手書きは0.4前後)
  - 今は、90°の控除値から逆算した理論式(内R = 板厚と仮定)で計算する(SUS t1.5の45°で約0.89)。「要確認」の表示も出す
  - **設定の曲げ控除表に「45°」の欄を追加**(`Views/SettingsViews.swift`)。会社の45°の控除値を入れると、その値を使う。0のままなら理論式
  - 使う順番: 図面の手書きの控除 → 設定の45°の値 → 理論式
- **「図面と見比べる」の合わせ方を直した**(`Views/PreviewViews.swift` の `PhotoAlignment.robustSolve`)
  - 例: 取り出し口フタ L-5012-00004-002(SUS304 t1.5、8-φ4.5・フランジに6-M3)で、データの穴の位置は正しいのに、全部の穴に「ずれ約60〜70mm」と出ていた
  - 原因: フランジの穴(側面図など別のビューに描かれた穴)も含めて、全部の穴で写真の縮尺・傾きを最小二乗で合わせていたため、全体が引っぱられてずれていた
  - 修正: 穴2つの組をすべて試し、ずれが許容内(2%か3mmの大きい方)に収まる穴がいちばん多い合わせ方を選び、その穴だけで合わせ直す。合わない穴は「ずれ」として表示するが、合わせには使わない
  - さらに、合わなかった穴を図(ビュー)ごとのまとまりに分け、まとまりごとに平行移動だけで合わせ直して比べる(第三角法の図は同じ縮尺・同じ向きのため)。フランジのM3のように側面図に描かれた穴も「別の図と一致」「別の図とずれ約○mm」と判定できる。重ねる表示でも、その穴の四角をデータの近くに出す
- **会社名を②の画面に表示・入力できるようにした**(`Views/ResultView.swift` の `CompanyField`、`Views/ExportView.swift`)
  - 会社名はDXFの保存フォルダ(DXF → 会社 → 素材 → 板厚)の分類に使うが、v3.9では③ DXF画面でしか見えなかった。会社名の無い図面は気づかないまま「会社名未確定」のフォルダに入っていた
  - 「② 部品を確かめる」「② 形を確かめる」の上に会社名の欄を追加。読み取れなかったときは「会社名を読み取れませんでした。入力しないと『会社名未確定』のフォルダに保存されます」と表示し、その場で入力できる。入っていれば保存先のフォルダ名を表示
  - ③ DXF画面でも、会社名が空なら注意を表示
  - AIへの指示: 会社名はロゴ・図番の頭・スタンプからも探し、無ければ空にする(推測で入れない)
- **DXFファイルを見る機能を追加**(`Views/ExportView.swift` の `DXFReader`・`DXFFileView`・`SavedDXFListView`、`Views/HomeView.swift`)
  - 最初の画面に「保存したDXFを見る」。「ファイル」アプリに保存したDXF(DXF → 会社 → 素材 → 板厚)をフォルダごとに一覧表示し、タップで開く
  - ③ DXF画面の各ファイルに「DXFを見る」ボタン。画面の下にも「保存したDXFを見る」
  - 開いた画面では、DXFファイルそのもの(LINE / ARC / CIRCLE)を読み込んで描く。大きさ・線/円弧/円の数・丸穴の径と位置(左下が0,0)を表示。図をタップで拡大、「このファイルを送る・保存する」で共有
  - アプリの中の形ではなく、会社のパソコンに送るファイルの中身そのものを確かめられる
- **材質・板厚ごとにまとめて出す**(`Views/ExportView.swift` の `BatchExportView`・`BatchGroupView`、`Export/DXFWriter.swift` の `Exporter.sheetCount`)
  - 最初の画面に「材質・板厚ごとにまとめて出す」。図面をまたいで同じ材質・板厚の部品を集め、「SUS304 t1.5 部品12種・合計18枚・図面5枚」のように表示
  - 材質・板厚を選ぶと部品の一覧(タップで選ぶ・外す)。「選んだ部品のDXFを作って送る」で1回で送れる(「ファイル」アプリのフォルダにも保存)。送ったあと「この部品の図面を、まとめて加工済みにする」
  - 初めは未加工の図面だけが対象。「加工済みの図面も含める」で切り替え
  - 以前からあった `Exporter.groups`(どこからも使われていなかった)を使っている
- **部品ごとの「確認済み」**(`Models/Models.swift` の `Part.confirmed` ほか、`Views/ResultView.swift` の `ConfirmPartButton`)
  - 「② 形を確かめる」の各部品の下に「確認済み」ボタン。上に「確認済み ○ / ○」
  - 確認したときの展開・板厚・数量を一緒に保存し、あとで形・板厚・数量が変わると自動で未確認に戻る(`Part.isConfirmed`)
  - ③ DXF画面と、まとめて出す画面で、確認済みでない部品をオレンジで知らせる(DXFは作れる。止めはしない)
- **加工済みの印**(`DrawingRecord.processed`・`processedAt`、`Views/HomeView.swift`、`Views/ResultView.swift`)
  - 「② 形を確かめる」の上に「加工済みにする」ボタン。最初の画面の一覧で行を右へスワイプしても付け外しできる
  - 最初の画面の一覧を「これまでの図面(未加工)」と「加工済み」(日付つき)に分けて表示
- **注意の色分け(赤=必須、オレンジ=要確認)**(`Views/SettingsViews.swift` の `Attention`・`AttentionTag`・`AttentionBackground`・`AttentionLegend`、各画面)
  - 入れないとDXFを作れない・正しく作れない所(板厚・材質)が空なら、背景を赤・白い枠にして「必須」の札を付ける。板厚の入力欄の見本の文字も「必須」にした
  - AIの推定(板厚の推定、推定した頂点・穴、要確認のまとめ、確かめてほしいこと)は、背景をオレンジ・オレンジの枠にして「要確認」の札を付ける
  - 「このままではDXFを作れません」(板厚未確定など)は赤、「確かめてほしいこと」はオレンジに分けた
  - 会社名が空のときはオレンジ(DXFは作れるが「会社名未確定」のフォルダに入るため)
  - ②の2つの画面の上に色の意味(必須=必ず入力/要確認=推定・図面と確認)を表示
  - 対象: ② 部品を確かめる(材質・板厚)、② 形を確かめる(部品カードの材質・板厚・要確認・確かめてほしいこと)、数値を直す(材質・板厚・推定した穴・頂点・側壁の穴)

## v3.8 の変更点(「ファイル」アプリに SHEET MASTER のフォルダが出ない不具合の修正)
- **原因**: v3.5 で「ファイル」アプリにアプリのフォルダを出す設定(UIFileSharingEnabled・LSSupportsOpeningDocumentsInPlace)を、ビルド設定の `INFOPLIST_KEY_…` で入れていた。この2つは Xcode の自動生成 Info.plist では使えない項目のため、ビルドしたアプリに入っておらず、「このiPhone内」に SHEET MASTER のフォルダが出なかった(DXFはアプリの中には保存されていたが、外から見えなかった)
- **修正**: プロジェクトのいちばん上(`SheetMaster.xcodeproj` と同じ場所)に `SheetMaster-Info.plist` を追加し、この2つの項目を書いた。ビルド設定の `INFOPLIST_FILE` でこのファイルを指定し、自動生成の Info.plist と合わせて使う(`GENERATE_INFOPLIST_FILE = YES` のまま。ほかの項目は今までどおり)
  - **このファイルは必ず一緒に入れること**(無いとビルドエラーになる)。`SheetMaster` フォルダの中には入れない(入れるとリソースと重なってビルドエラーになる)
  - プロジェクトファイルの変更は、上の2行を `INFOPLIST_FILE = "SheetMaster-Info.plist";` 1行に置き換えた所(Debug・Release)と、バージョン番号の2か所だけ
- **③ DXF画面で、保存したフォルダ名をタップすると「ファイル」アプリでそのフォルダを開く**(`Views/ExportView.swift`)
- 確かめ方: 入れたあと ③ DXF画面を一度開く → 「ファイル」アプリ → このiPhone内 に**アプリのアイコン付きの「SHEET MASTER」**フォルダが出て、DXF → 会社 → 素材 → 板厚 の順に入っていること
- v3.7 の変更(組立図の板の分け方)もすべて含む。バージョン表記を 3.8 に変更。ビルド番号だけ前回より大きくする
- 注意: この版も Swift のビルド環境が無い所で作ったため、ビルドで確かめていない

## v3.7 の変更点(手書きの作り方が無くても、組立図の板の分け方を正しく決める)
対象の例: 日新電子工業 DM261434J-M002 不良品受箱(SUS304 t1.2、前板400・底349・後板250、側板349×400×2、取付板t2)。
v3.6 では、前板・底・後板を3枚の平板に分け(本来はU字1枚)、側板を断面に合わせた台形にしていた(本来は側面図どおりの長方形+R5)。前板だけ幅600、ほかは597.6と食い違っていた。

- **AIへの指示に【作り方を決める手順】を追加**(`Reading/Prompts.swift` の段階A)
  - 手順1: 立体の面(前・後・左・右・上・底)を数える。破線は隠れ線で、その面は実在する。主投影図に見える面を「前」とする
  - 手順2: 隣り合う面を曲げでつなぐか溶接でつなぐかを、板金の一般的な作り方で決める(同じ板厚で辺を共有する面は曲げが基本。溶接にするのは、展開で重なる・板厚違い・溶接記号がある・定尺を超える場合だけ)。一列に並ぶ3面は曲げ線が長い方向の並びを1枚にし、残りを端板にする。前と後の高さが違うU字も1枚
  - 手順3: 端板を外側に当てるなら、曲げた板の長さ = 全体 − 板厚×2。同じ辺に沿う板の長さをそろえる
  - 手順4: 面ごとに、それを作る部品を対応させる
- **妻板・側板の形**: その板が正面に見えるビュー(側面図など)に外形があれば、その線どおりにする。本体の断面から形を作るのは、どのビューにも外形が無いときだけ(段階A・段階Bの両方)
- **AIの回答に「組立品の面とつなぎ方」(assembly)を追加**し、アプリが部品一覧と照合する(`Reading/DrawingReader.swift` の `assemblyProblems`)
  - 曲げでつなぐ2面が別の部品になっている/面の部品が一覧に無い/同じ板厚の面が一列に並び両側とも溶接の別板になっている(前板・底・後板を3枚に分けた形)を見つけたら、理由を添えて段階Aを1回だけ自動で読み直す
  - それでも残る食い違いは「確かめてほしいこと」に「部品の分け方: …」として出す
  - 溶接にする理由がはっきりしていれば(厚板の溶接箱など)溶接のままでよいとAIに伝えている
- **部品ごとの面と曲げを段階Bに渡す**(`applyAssembly`)
  - 各部品の説明に「この部品の面」「曲げでつなぐ面」「溶接で付く相手」「端板は外側に当てる」を書き足し、展開の読み取りで面ごとに別の板にしないようにした
  - 曲げでつなぐ面の数が部品一覧の曲げ回数より多ければ、曲げ回数を直す(曲げ線の読み落としの自動読み直しが効く)
  - 「② 部品を確かめる」画面の説明に【作り方】(曲げ・溶接・端板の付け方)を表示
- 段階Bの指示に、前と後の高さが違うU字の faces の書き方の例を追加
- **データの形は変えていない**(assembly は段階Aの回答の中だけ。以前に読み取った図面もそのまま開ける)

## v2.6 の変更点(読み取りの失敗対策)
- **通信をストリーミング(少しずつ受信)に変更**(`Reading/ClaudeClient.swift`)。
  v2.5 は回答が全部できるまで通信が無言になり、曲げのある図面では数分待った末に接続が切れて「読み取れない」になっていた。
  読み取り中は「受信 ○○字」が増えていくので、動いているかどうかが見える。
- **AIの「考える機能(thinking)」を使用**。使えないモデル・キーの場合は自動で外して再送する。
- **曲げ部品の展開方式を変更**(`Geometry/Geometry.swift` の `FaceBuilder`、`Models/Models.swift` の `FaceModel`)。
  AIには「基準面+フランジの外寸と穴の位置」だけを答えさせ、展開座標・曲げ控除・角の逃げ・U溝・角Rはアプリが計算する。
  v2.5 の「外寸を並べて控除を引く」方式は、箱形(4辺曲げ)だと角の寸法が左右でずれていた。
- 読み取り中は画面が消えないようにし、アプリを一瞬切り替えても通信を続ける。
- 「数値を直す」画面に、曲げ部品の面の寸法・穴・切欠きの入力欄を追加。
- **新しいファイルは追加していない**(既存ファイルの中身だけ変更)。プロジェクトファイルの変更は不要。
- `Config.xcconfig` は前回の Bundle ID・Team ID のまま、**ビルド番号だけ前回より大きく**する。
- 以前に読み取った図面は、そのまま開ける。曲げ部品は「指示して読み直す」を押すと新方式で読み直す。
